# Method Catalog

8 个提升 Agent 有效性的核心方法论。随着模型能力提升，这些原则可以用精炼的提示调动，无需冗长说明。

## 1. First Principles (第一性原理)

**核心：** 回归问题本质，验证问题真实存在

**何时使用：**
- 问题描述模糊或二手转述
- 需求不清晰，缺少具体细节
- 多轮对话后偏离原始目标
- 修复验证：确认问题复现 → 根因 → 修复后变化

**应用方式：**
```
在开始解决前，先验证：
1. 问题能否复现？具体表现是什么？
2. 根本原因是什么？（非表象）
3. 预期结果是什么？如何判断已解决？
```

**Example：**
- ❌ "用户说登录慢" → 立即优化代码
- ✅ "登录慢" → 复现步骤？慢多少？哪个环节慢？测量基线？

## 2. Adversarial Review (对抗式审查)

**核心：** 独立 agent 专门找反例、遗漏、失败场景

**何时使用：**
- 关键决策（架构选型、安全设计）
- 质量要求高的产出（生产代码、发布文档）
- 多 agent 协作需要交叉验证
- 防止一个 agent 错误传播

**应用方式：**
```
实施步骤独立审查：
1. 实施 agent 完成任务（不参与审查）
2. 审查 agent 寻找：反例、边界条件、未测场景
3. 要求审查 agent 提供具体证据
4. 实施 agent 根据发现修正
```

**Example：**
- 实施："设计用户权限系统" → 完成设计文档
- 审查："找出权限设计的安全漏洞、边界情况、未考虑场景"

---

## 3. Ablation Experiment (消融实验)

**核心：** 移除组件，对比结果，证明必要性

**何时使用：**
- 评估某规则/工具/配置是否真正需要
- 优化性能时判断哪些改动有效
- 简化复杂系统时识别可移除部分
- 验证某个依赖的实际作用

**应用方式：**
```
对每个待验证组件：
1. 记录当前完整状态的表现（baseline）
2. 移除目标组件，保持其他不变
3. 运行相同测试，对比结果
4. 量化影响：必需/优化/无效
```

**Example：**
- "这个缓存层是否必需？" → 移除后测试响应时间、成功率
- "提示词中的这段说明有用吗？" → 对比有/无该段时的输出质量

---

## 4. Occam's Razor (奥卡姆剃刀)

**核心：** 先做最简单、能工作的版本

**何时使用：**
- 面对新问题，不确定最佳方案
- 倾向过度设计（过早抽象、过多配置）
- 需要快速验证可行性
- Build in Public 阶段，用真实反馈迭代

**应用方式：**
```
优先级排序：
1. 能解决核心问题的最少代码/配置
2. 跑通最简单路径（hard-code 也可以）
3. 获得真实使用反馈
4. 根据实际需求迭代复杂度
```

**Example：**
- ❌ "构建配置系统" → 设计 YAML + 校验 + 热重载 + UI
- ✅ "构建配置系统" → 单个 JSON 文件 + 重启生效 → 根据痛点逐步增强

---

## 5. List Uncertainties (列出不确定性)

**核心：** 明确交代哪些是事实，哪些是推测

**何时使用：**
- 信息不完整但需要给出方案
- 风险评估和决策说明
- 防止 agent "自信地错误"
- 复杂推理链需要透明化

**应用方式：**
```
在输出中明确标注：
1. 已验证的事实（有证据支撑）
2. 合理推测（基于经验但未验证）
3. 未测场景（需要补充测试）
4. 缺少证据的结论（需要进一步调查）
5. 什么证据会推翻当前判断
```

**Example：**
```
✅ 分析报告：
- 确认：日志显示 API 超时（证据：error.log L234）
- 推测：可能是数据库连接池耗尽（未验证查询日志）
- 未测：高并发场景下的表现
- 推翻条件：如果超时发生在数据库查询前，则原因在网络层
```

## 6. Independent Thinking (独立思考)

**核心：** 先独立判断，再参考他人结论

**何时使用：**
- 多 agent 协作场景
- 防止"羊群效应"（一个错，全跟着错）
- 需要多视角分析同一问题
- 重要决策需要多方验证

**应用方式：**
```
协作流程：
1. 每个 agent 独立分析，给出结论 + 依据
2. 不提前共享中间结果
3. 所有结论提交后，开始讨论
4. 重点关注分歧点，要求各自解释理由
5. 基于证据强度达成共识
```

**Example：**
- ❌ Agent A 分析 → Agent B 看到 A 的结论 → B 倾向认同
- ✅ Agent A、B、C 同时独立分析 → 汇总：A 认为 X，B 认为 Y，C 认为 X → 讨论 B 的不同依据

## 7. Critical Thinking (批判性思维)

**核心：** 区分观察和推测，检查证据

**何时使用：**
- 验证任何看起来完整的分析
- 审查他人（或自己）的结论
- 防止"因为写得好就是对的"偏见
- 需要高可信度的输出

**应用方式：**
```
对每个结论检查：
1. 这是直接观察还是推理？
2. 证据是什么？来源可靠吗？
3. 有没有其他解释？
4. 如果证据 X 出现，结论是否仍成立？
5. 哪些前提假设必须为真？
```

**Example：**
```
声明："系统变慢是因为内存泄漏"
批判性检查：
- 证据：内存使用确实增长（观察）
- 推理：增长导致变慢（需验证：时间相关性？其他资源？）
- 替代解释：数据量增长？缓存策略变化？
- 推翻证据：如果重启后立即变慢，则非内存泄漏
```

## 8. High Cohesion, Low Coupling (高内聚、低耦合)

**核心：** 相关逻辑聚合，模块边界清晰

**何时使用：**
- 架构设计和模块划分
- 代码重构，降低复杂度
- Agent 任务分配（明确上下文边界）
- 提高可维护性和可测试性

**应用方式：**
```
设计检查：
1. 高内聚：同一模块内的功能是否紧密相关？
2. 低耦合：模块间通过清晰接口交互，修改一个不影响其他？
3. 单一职责：每个模块只做一件事？
4. Agent 视角：改这个模块时，需要理解多少其他代码？
```

**Example：**
- ❌ UserService 包含：用户验证、邮件发送、订单处理、日志记录
- ✅ UserService（用户 CRUD）、AuthService（验证）、EmailService（邮件）、OrderService（订单）

**对 Agent 的影响：**
- 耦合度低 → agent 只需加载相关模块的上下文
- 边界清晰 → 验证范围明确，测试更容易

## 组合使用建议

| 场景 | 推荐组合 |
|------|----------|
| 新功能开发 | Occam's Razor → First Principles → Adversarial Review |
| Bug 修复 | First Principles → Critical Thinking → (验证后) Adversarial Review |
| 性能优化 | Ablation Experiment → First Principles |
| 架构重构 | High Cohesion Low Coupling → Ablation Experiment → Adversarial Review |
| 多 Agent 协作 | Independent Thinking → Adversarial Review |
| 复杂决策 | List Uncertainties → Critical Thinking → Independent Thinking |

## 与模型演进的关系

**过去：** 需要 1000 行提示词详细说明"如何做对抗审查"

**现在：** 模型已内化方法论，只需触发词：
```
"Use adversarial review: find counter-examples and failure scenarios"
```

**未来焦点：**
- ✅ 选择合适方法论（路由）
- ✅ 定义验证标准（判断做对了）
- ✅ 提供领域上下文（特殊约束）
- ❌ 不再需要教"什么是对抗审查"
